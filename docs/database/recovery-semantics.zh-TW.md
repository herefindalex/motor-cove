## 重建

重建的意思是：信任已驗證的本地`indexed_blocks`和`chain_events`，然後重新產生投影。在清除派生行之前，它會驗證規範覆蓋範圍、掃描完成標記、日誌計數和摘要、事件包絡、解碼器相容性、檢查點覆蓋範圍、部署和日誌範圍。來源故障使先前的投影保持完整，並需要重新索引或明確支援的復原路徑。

目錄和部署行永遠不會從鏈事件重建。僅在受控工作單元中重播完成後，成功發布才會取代投影建置元資料。

## 重建索引

重新索引作為來源權威來源返回到鏈。它驗證部署運行時身份，修復合格的目標區塊和哈希，記錄操作所有權，並重新取得標頭和日誌。重組處理可能會保留移位的區塊和事件證據，同時變更哪個分支是規範的。 投影狀態和檢查點隨後收斂於相同的固定目標策略。

重新索引不會重設鏈、重新設定目錄權威來源或建立不同的部署代。

## 備份

標準備份透過支援的備份路徑擷取 SQLite 並將其校驗和綁定到清單。對於已部署的環境，準備情況還取決於相容的部署、種子日誌、引導收據、來源條件、模式契約和生命週期證據。內部遷移或來源刷新存檔是操作綁定的證據，而不是標準恢復來源。

權威來源矩陣中的備份重要性描述的是可恢復性，而不是選擇性檔案複製。 SQLite 快照始終包含完整的實體表集。

## 恢復

恢復安裝歷史資料庫產生。在隔離活動資料庫之前，它會驗證所選的標準備份、來源校驗和、部署描述符和活動生命週期 sidecar。然後，它會暫存資料庫，對暫存的位元組重複清單 SHA-256 檢查，並在隔離或發布任何內容之前驗證架構、歷史記錄、完整性和部署。因此，驗證和複製之間的來源變更會保留活動資料庫並記錄失敗的復原標記。恢復不會回滾 Anvil 或任何鏈，並且恢復的投影可能需要追趕或明確恢復。

## 遷移

遷移是物理架構更改的唯一支援的路徑。它驗證已知的本機歷史記錄，建立並記錄安全備份，套用有序的 SQL，驗證完整性和外鍵，並發布匹配的 `db_contract`。應用的遷移是不可變的。復原必須使用持久操作階段和重新驗證的備份證據。

## 重置

對於線束擁有的本地環境來說，重置是一種明確的破壞性操作。它驗證託管環境所有者和頂級遏制，獲取其維護門，然後在記錄意圖或更改託管本地鏈之前使用 `lstat` 和 `realpath` 重新檢查資料庫和報告目錄。生成狀態清理在刪除之前重複相同的檢查。重置不是備份、遷移、重建或部署不匹配的修復技術。

## 故障選擇

當經過驗證的本地來源證據完整且僅派生狀態值得懷疑時，請使用重建。當本機來源完整性、規範身分、解碼器相容性或來源摘要不可信時，請使用重新索引。對經過驗證的相容快照使用還原。僅對明確一次性擁有的本地環境使用重置。這些路徑均未授權重新提交錢包操作。

## 備份目的與復原策略

清單的恢復策略和維護存檔的目的回答了不同的問題：

| 證據                     | 目的                                                                           | 普通 `db:restore` 資格                                     |
| ------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| `STANDARD`備份           | 就緒來源的完整快照；已部署的快照也綁定部署、seed-日誌和 bootstrap-receipt 證據 | 已部署的快照經過驗證和活動產生檢查後合格；不支援部署前復原 |
| `EVIDENCE_ONLY`備份      | 當來源就緒或維護狀態阻止正常恢復聲明時保留位元組                               | 不符合資格                                                 |
| `MIGRATION_SAFETY`存檔   | 將遷移前快照綁定到遷移操作及其復原證明                                         | 不符合正常恢復源的條件                                     |
| `SOURCE_REFRESH_ARCHIVE` | 在來源刷新重新索引之前保留可疑或移位的來源                                     | 不符合正常恢復源的條件                                     |

後兩者是記錄在純證據檔案中的操作目的；它們不是非常正常的恢復策略。標準備份擁有共用引導程式所有權。部署的標準快照需要種子日誌和引導收據作為一對。它們的存在本身並不能證明完整：`bootstrap-receipt.json` 是針對 `formatVersion`、`environmentId`、`deploymentId`、`targetBlock`、`targetHash`、`projectionBuildId` 和 `completedAt` 進行原子發布和驗證的。備份和還原根據快照的身份驗證複製的收據；半發布的引導程式不被接受為就緒快照。

## 恢復建立了什麼

恢復在維護鎖定之前擁有獨佔引導程式所有權。它會驗證所選的標準備份和活動 sidecar，將資料庫複製到暫存，將暫存位元組與清單校驗和進行比較，並在隔離活動資料庫和安裝候選資料庫之前檢查暫存架構、歷史記錄、完整性和部署身分。它拒絕不同的活動引導生成，而不是將其 sidecar 與恢復的資料庫結合。失敗的隔離前檢查會將活動資料庫保留在原位並記錄失敗的維護狀態。

成功的復原會建立相容的、經過檢查的本地位元組和架構。它並不能確定鏈頭尚未前進、保存的投影已被趕上、歷史對帳報告是當前的、或者保存的工人心跳是最新的。這些說法需要隨後的即時觀察或適當的明確恢復操作。

## 合格目標和即時狀態

在即時運行時，當目標存在時為 `eligibleTarget = observedHead - indexingDepth`。 `CURRENT` 需要在該合格目標處有經過驗證的檢查點；如果還有更多符合條件的區塊，那麼提交一批是不夠的。固定的維護reindex目標是其追趕完成條件，而後期活`CURRENT`仍然取決於工人的實際頭部觀察。高於合格目標的檢查點需要明確重新索引，而不是普通的 `CURRENT` 轉換。

呈現給讀者的最後已知的投影狀態和觀察新鮮度是截然不同的；請參閱[時間語義](temporal-semantics.zh-TW.md)。

## 恢復情形及觀察時間

`RECOVERY_REQUIRED` 是持久的完整性證據。普通的Indexer啟動、提交、陳舊和當前轉換無法清除它。維護僅出於僅支援投影器的原因選擇重建；規範或來源懷疑需要重新索引。 Reindex透過倒帶、重播和追趕來保留原因，只有在驗證了目標錨點後才將其釋放到`SYNCING`。失敗的操作保留其標記和復原要求。

對帳仍然可以透過其維護擁有的資料庫連線保存診斷 `UNVERIFIABLE` 報告。此報告路徑不會清除障礙或允許普通的 Indexer 寫入。

本地日誌重建可能會更改投影建置和狀態，但它不會推進 `worker_heartbeat_at` 或證明新的 RPC 觀測。讀者的新鮮感仍然基於實際工人的觀察證據。部署的標準備份需要經過驗證的引導收據與其種子日誌配對；驗證會重新檢查複製的收據的身份和架構。
