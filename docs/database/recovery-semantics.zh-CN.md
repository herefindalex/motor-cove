# 数据库恢复语义

## 重建

重建的意思是：信任已验证的本地`indexed_blocks`和`chain_events`，然后重新生成投影。在清除派生行之前，它会验证规范覆盖范围、扫描完成标记、日志计数和摘要、事件包络、解码器兼容性、检查点覆盖范围、部署和日志范围。源故障使之前的投影保持完整，并需要重新索引或明确支持的恢复路径。

目录和部署行永远不会从链事件中重建。仅在受控工作单元中重播完成后，成功发布才会替换投影构建元数据。

## 重建索引

重新索引作为源权威来源返回到链。它验证部署运行时身份，修复合格的目标块和哈希，记录操作所有权，并重新获取标头和日志。重组处理可能会保留移位的块和事件证据，同时更改哪个分支是规范的。 投影状态和检查点随后收敛于相同的固定目标策略。

重新索引不会重置链、重新设定目录权威来源或创建不同的部署代。

## 备份

标准备份通过支持的备份路径捕获 SQLite 并将其校验和绑定到清单。对于已部署的环境，准备情况还取决于兼容的部署、种子日志、引导收据、源条件、模式契约和生命周期证据。内部迁移或源刷新存档是操作绑定的证据，而不是标准恢复源。

权威来源矩阵中的备份重要性描述的是可恢复性，而不是选择性文件复制。 SQLite 快照始终包含完整的物理表集。

## 恢复

恢复安装历史数据库生成。在隔离活动数据库之前，它会验证所选的标准备份、源校验和、部署描述符和活动生命周期 sidecar。然后，它会暂存数据库，对暂存的字节重复清单 SHA-256 检查，并在隔离或发布任何内容之前验证架构、历史记录、完整性和部署。因此，验证和复制之间的源更改会保留活动数据库并记录失败的恢复标记。恢复不会回滚 Anvil 或任何链，并且恢复的投影可能需要追赶或显式恢复。

## 迁移

迁移是物理架构更改的唯一受支持的路径。它验证已知的本机历史记录，创建并记录安全备份，应用有序的 SQL，验证完整性和外键，并发布匹配的 `db_contract`。应用的迁移是不可变的。恢复必须使用持久操作阶段和重新验证的备份证据。

## 重置

对于线束拥有的本地环境来说，重置是一种明确的破坏性操作。它验证托管环境所有者和顶级遏制，获取其维护门，然后在记录意图或改变托管本地链之前使用 `lstat` 和 `realpath` 重新检查数据库和报告目录。生成状态清理在删除之前重复相同的检查。重置不是备份、迁移、重建或部署不匹配的修复技术。

## 故障选择

当经过验证的本地源证据完整且仅派生状态值得怀疑时，请使用重建。当本地源完整性、规范身份、解码器兼容性或源摘要不可信时，请使用重新索引。对经过验证的兼容快照使用还原。仅对明确一次性拥有的本地环境使用重置。这些路径均未授权重新提交钱包操作。

## 备份目的和恢复策略

清单的恢复策略和维护存档的目的回答了不同的问题：

| 证据                     | 目的                                                                         | 普通 `db:restore` 资格                                     |
| ------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `STANDARD`备份           | 就绪源的完整快照；已部署的快照还绑定部署、seed-日志和 bootstrap-receipt 证据 | 已部署的快照经过验证和活动生成检查后合格；不支持部署前恢复 |
| `EVIDENCE_ONLY`备份      | 当源就绪或维护状态阻止正常恢复声明时保留字节                                 | 不符合资格                                                 |
| `MIGRATION_SAFETY`存档   | 将迁移前快照绑定到迁移操作及其恢复证明                                       | 不符合正常恢复源的条件                                     |
| `SOURCE_REFRESH_ARCHIVE` | 在源刷新重新索引之前保留可疑或移位的源                                       | 不符合正常恢复源的条件                                     |

后两者是记录在纯证据档案中的操作目的；它们不是非常正常的恢复策略。标准备份拥有共享引导程序所有权。部署的标准快照需要种子日志和引导收据作为一对。它们的存在本身并不能证明完整：`bootstrap-receipt.json` 是针对 `formatVersion`、`environmentId`、`deploymentId`、`targetBlock`、`targetHash`、`projectionBuildId` 和 `completedAt` 进行原子发布和验证的。备份和恢复根据快照的身份验证复制的收据；半发布的引导程序不被接受为就绪快照。

## 恢复建立了什么

恢复在维护锁定之前拥有独占引导程序所有权。它会验证所选的标准备份和活动 sidecar，将数据库复制到暂存，将暂存字节与清单校验和进行比较，并在隔离活动数据库和安装候选数据库之前检查暂存架构、历史记录、完整性和部署身份。它拒绝不同的活动引导生成，而不是将其 sidecar 与恢复的数据库结合起来。失败的隔离前检查会将活动数据库保留在原位并记录失败的维护状态。

成功的恢复会建立兼容的、经过检查的本地字节和架构。它并不能确定链头尚未前进、保存的投影已被赶上、历史对账报告是当前的、或者保存的工人心跳是最新的。这些说法需要随后的实时观察或适当的明确恢复操作。

## 合格目标和实时状态

在实时运行时，当目标存在时为 `eligibleTarget = observedHead - indexingDepth`。 `CURRENT` 需要在该合格目标处有经过验证的检查点；如果还有更多符合条件的区块，那么提交一批是不够的。固定的维护reindex目标是其追赶完成条件，而后期活`CURRENT`仍然取决于工人的实际头部观察。高于合格目标的检查点需要显式重新索引，而不是普通的 `CURRENT` 转换。

呈现给读者的最后已知的投影状态和观察新鲜度是截然不同的；请参阅[时间语义](temporal-semantics.zh-CN.md)。

## 恢复情况及观察时间

`RECOVERY_REQUIRED` 是持久的完整性证据。普通的Indexer启动、提交、陈旧和当前转换无法清除它。维护仅出于仅支持投影器的原因选择重建；规范或来源怀疑需要重新索引。 Reindex通过倒带、重放和追赶来保留原因，只有在验证了目标锚点后才将其释放到`SYNCING`。失败的操作保留其标记和恢复要求。

对账仍然可以通过其维护拥有的数据库连接保存诊断 `UNVERIFIABLE` 报告。该报告路径不清除障碍或允许普通的 Indexer 写入。

本地日志重建可能会更改投影构建和状态，但它不会推进 `worker_heartbeat_at` 或证明新的 RPC 观察。读者的新鲜感仍然基于实际工人的观察证据。部署的标准备份需要经过验证的引导收据与其种子日志配对；验证会重新检查复制的收据的身份和架构。
