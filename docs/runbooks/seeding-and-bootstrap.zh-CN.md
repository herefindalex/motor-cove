# 如何播种和引导本地环境

[English](seeding-and-bootstrap.md) · [繁體中文](seeding-and-bootstrap.zh-TW.md)

此 Runbook 定义本地种子和引导行为。

## 何时使用

启动一个托管 Anvil 后，使用 bootstrap 来协调新拥有的本地环境。不要使用种子作为重置，不要针对公共 RPC 运行它，也不要使用它来将用户的销售或所有权恢复到初始状态。

## 目标序列

1. 验证所有者标记、环回 RPC、Anvil 客户端、链 ID 和部署身份。
2. 获得独家环境引导程序所有权。标准备份采用共享引导程序
   所有权和恢复在维护锁定之前拥有独占所有权，因此两者都不能在整个生命周期中发布或安装快照。
3. 迁移和验证数据库、部署合约并验证清单代码/getters/块。
4. 每次链上种子交易前，持久记录`PREPARED`；然后是 `SUBMITTED` 和 `VERIFIED`。
5. 从收据和事件中获取代币/销售 ID，然后以事务方式种子目录和绑定。
6. 捕获目标块/哈希，运行一次正常的摄取应用程序，并断言检查点，
   目录、销售、索赔和所有权状态。
7. 写入引导收据、清除标记并释放锁定。

重试之前会检查已知的哈希值。可能在没有持久哈希的情况下广播的结果必须以 `UNKNOWN` 停止。完成的引导程序验证历史证据，不会再次铸造或列出。

## 当前实施情况

`seed:catalog` 对一个固定的本地数据集实现原子幂等性和 `SEED_CONFLICT`。 `dev:bootstrap`通过环境拥有的`seed-journal.json`部署本地合约，注册部署证据，种子目录绑定，通过捕获的块/哈希进行追赶，并写入收据。每个部署、铸造、批准和列出步骤都将其参数绑定到意图摘要。非阻塞所有权锁覆盖了这个完整的回调，因此同一环境的两个引导进程不能同时进入链提交。使用已知哈希重新运行等待该收据；经过验证的步骤会重新检查相同的收据并且不再提交。搁浅的 `PREPARED` 步骤或结果无法证明的提交调用将变为 `UNKNOWN` 并停止以供操作员审查。该命令永远不会猜测是否应该再次发送不明确的事务。

已部署的标准备份包含 `seed-journal.json` 和 `bootstrap-receipt.json`，或者对于在此引导路径之外管理的部署，两者都不包含。不完整的一对将被拒绝。在引导程序内创建的迁移安全快照显式地重用调用者的生命周期所有权，而不是尝试重新获取不可重入锁。

目录播种获取现有的专用维护门，然后在打开数据库或更改行之前检查持久标记。来自不完整操作的 `PENDING` 或 `FAILED` 标记返回 `MAINTENANCE_INCOMPLETE`；目录行、部署绑定和标记保持不变。请勿移除或忽略标记以继续播种。对记录的操作使用身份匹配恢复命令。

一旦 `deployment.json` 存在，重新运行将验证运行时代码哈希值和部署 ID getter，然后仅执行数据库注册、目录幂等性和追赶。它不会铸造、列出或恢复用户拥有的链状态。不要编辑日志来强制进度；将其与环境一起保存并诊断RPC和交易证据。

## 验证

`pnpm test:seeds` 涵盖临时 SQLite 环境中的 DB-23–DB-25 和 DB-29，包括拒绝更改的种子版本而不覆盖所应用的数据集。 日志单元测试涵盖成功转换、已知哈希恢复、验证收据重新验证、身份/意图不匹配以及保守的 `UNKNOWN` 处理。真实堆栈测试涵盖了新的事件衍生引导程序以及用户结算、退款、提现和 NFT 回收后的重新运行。两进程回归证明，当所有者处于活动状态时，只有一个引导回调进入。维护测试证明，当存在不完整的标记时，目录播种是只读的。锁生命周期测试包括正常退出、释放前信号退出、重复释放和复合清理。广播到哈希持久性窗口中真正的进程终止注入尚未得到验证。参见[数据库矩阵](../testing/database-acceptance-matrix.zh-CN.md)。

## 专用本地节点声明

在 bootstrap 确认预期的链 ID 后，在提交部署或种子交易之前，它会声明为托管环境配置的环回 RPC 端点。索赔由工作区范围的 `managed-nodes.lock` 序列化。在链写入之前，使用相同标准化端点的第二个环境会被拒绝。

将生成的 `managed-node.json` 保留在环境生命周期中。丢失或编辑的绑定属于所有权失败；故意重新创建环境，而不是复制另一个环境的绑定。

## 可恢复的哈希后持久性

如果在提交回调返回哈希后第一个 `SUBMITTED` 日志写入失败，则该命令仅重试日志写入。成功重试会将步骤保留为 `SUBMITTED`，记录 `POST_SUBMIT_PERSISTENCE_FAILURE` 类别，并返回 `CHAIN_SEED_POST_SUBMIT_PERSISTENCE_RECOVERED`。重新打开相同的环境并重新运行 bootstrap：它等待保存的哈希并且不会再次调用提交。任何哈希之前的失败仍然是 `SUBMIT_OUTCOME_UNKNOWN` 并需要操作员审查。

日志回归测试注入一个瞬态哈希后写入错误，并证明重新打开的日志无需第二次提交即可验证原始哈希。无哈希提交失败、搁浅的 `PREPARED` 步骤、更改的意图和更改的接收证据仍然会失败关闭。

## 托管绑定步骤

新的 bootstrap 部署 `VehicleNFT`，部署 `MotorCoveEscrow`，然后在铸造演示代币之前记录 `bind-vehicle-nft-escrow` 交易。绑定是一次性的，交易收据是链种子日志的一部分。通过读取 `VehicleNFT.motorCoveEscrow()` 并将结果与清单托管地址进行比较来验证它。仅当链上绑定仍然匹配时，现有清单才会被接受；缺少 getter 或不同的地址会在数据库引导之前返回 `DEPLOYMENT_MISMATCH`。

使用此绑定之前的合约字节码创建的环境无法就地升级；合约是不可升级的。保留该环境以供检查或在引导全新部署之前运行显式本地重置工作流程。 Bootstrap 绝不会隐式重置或替换现有环境。

## Bootstrap 完成 sidecar

Bootstrap 将 `deployment.json` 和 `bootstrap-receipt.json` 发布为完全不可变的 JSON sidecar：验证、写入和刷新操作唯一的临时文件，重命名到位，并同步包含的目录。恢复时，现有的最终文件必须解析并匹配其环境和部署。收据还验证其目标块/哈希、投影构建 ID 和完成时间。它的目标和构建ID是历史完成的证据；稍后的交易可能会推进链头，并且有效的重建可能会使用不同的当前投影构建。部署的标准备份需要此收据和配对种子日志。格式错误或冲突的最终内容会停止显式恢复操作。
