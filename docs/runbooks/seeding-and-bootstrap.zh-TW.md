# 如何播種和引導本地環境

[English](seeding-and-bootstrap.md) · [简体中文](seeding-and-bootstrap.zh-CN.md)

此 Runbook 定義本機種子和引導行為。

## 何時使用

啟動一個託管 Anvil 後，使用 bootstrap 來協調新擁有的本地環境。不要使用種子作為重置，不要針對公共 RPC 運行它，也不要使用它來將用戶的銷售或所有權恢復到初始狀態。

## 目標序列

1. 驗證擁有者標記、環回 RPC、Anvil 用戶端、鏈 ID 和部署身分。
2. 獲得獨家環境引導程式所有權。標準備份採用共享引導程序
   所有權和復原在維護鎖定之前擁有獨佔所有權，因此兩者都不能在整個生命週期中發布或安裝快照。
3. 遷移和驗證資料庫、部署合約並驗證清單程式碼/getters/區塊。
4. 每次鏈上種子交易前，持久記錄`PREPARED`；然後是 `SUBMITTED` 和 `VERIFIED`。
5. 從收據和事件中取得代幣/銷售 ID，然後以事務方式種子目錄和綁定。
6. 捕獲目標塊/哈希，運行一次正常的攝取應用程序，並斷言檢查點，
   目錄、銷售、索賠和所有權狀態。
7. 寫入引導收據、清除標記並釋放鎖定。

重試之前會檢查已知的雜湊值。可能在沒有持久哈希的情況下廣播的結果必須以 `UNKNOWN` 停止。完成的引導程序驗證歷史證據，不會再次鑄造或列出。

## 目前實施狀況

`seed:catalog` 對一個固定的本地資料集實現原子冪等性和 `SEED_CONFLICT`。 `dev:bootstrap`透過環境擁有的`seed-journal.json`部署本地合約，註冊部署證據，種子目錄綁定，透過捕獲的區塊/哈希進行追趕，並寫入收據。每個部署、鑄造、批准和列出步驟都將其參數綁定到意圖摘要。非阻塞所有權鎖定覆蓋了這個完整的回調，因此同一環境的兩個引導程序不能同時進入鏈提交。使用已知哈希重新運行等待該收據；經過驗證的步驟會重新檢查相同的收據並且不再提交。擱淺的 `PREPARED` 步驟或結果無法證明的提交呼叫將變為 `UNKNOWN` 並停止以供操作員審查。該命令永遠不會猜測是否應該再次發送不明確的事務。

已部署的標準備份包含 `seed-journal.json` 和 `bootstrap-receipt.json`，或在此引導路徑之外管理的部署，兩者都不包含。不完整的一對將被拒絕。在引導程式內建立的遷移安全快照明確地重複使用呼叫者的生命週期所有權，而不是嘗試重新取得不可重入鎖定。

目錄播種取得現有的專用維護門，然後在開啟資料庫或變更行之前檢查持久標記。來自不完整操作的 `PENDING` 或 `FAILED` 標記返回 `MAINTENANCE_INCOMPLETE`；目錄行、部署綁定和標記保持不變。請勿移除或忽略標記以繼續播種。對記錄的操作使用身份匹配恢復命令。

一旦 `deployment.json` 存在，重新執行將驗證執行時間程式碼雜湊值和部署 ID getter，然後僅執行資料庫註冊、目錄冪等性和追趕。它不會鑄造、列出或恢復使用者擁有的鏈狀態。不要編輯日誌來強制進度；將其與環境一起保存並診斷RPC和交易證據。

## 驗證

`pnpm test:seeds` 涵蓋臨時 SQLite 環境中的 DB-23–DB-25 和 DB-29，包括拒絕更改的種子版本而不覆蓋所應用的資料集。 日誌單元測試涵蓋成功轉換、已知雜湊恢復、驗證收據重新驗證、身份/意圖不匹配以及保守的 `UNKNOWN` 處理。真實堆疊測試涵蓋了新的事件衍生引導程序以及用戶結算、退款、提現和 NFT 回收後的重新運行。兩進程回歸證明，當擁有者處於活動狀態時，只有一個引導回調進入。維護測試證明，當存在不完整的標記時，目錄播種是唯讀的。鎖定生命週期測試包括正常退出、釋放前訊號退出、重複釋放和複合清理。廣播到哈希持久性視窗中真正的進程終止注入尚未得到驗證。參見[資料庫矩陣](../testing/database-acceptance-matrix.zh-TW.md)。

## 專用本機節點聲明

在 bootstrap 確認預期的鏈 ID 後，在提交部署或種子交易之前，它會宣告為託管環境配置的環回 RPC 端點。索賠由工作區範圍的 `managed-nodes.lock` 序列化。在鏈寫入之前，使用相同標準化端點的第二個環境會被拒絕。

將產生的 `managed-node.json` 保留在環境生命週期中。遺失或編輯的綁定屬於所有權失敗；故意重新建立環境，而不是複製另一個環境的綁定。

## 可恢復的哈希後持久性

如果在提交回呼返回雜湊後第一個 `SUBMITTED` 日誌寫入失敗，則該命令僅重試日誌寫入。成功重試會將步驟保留為 `SUBMITTED`，記錄 `POST_SUBMIT_PERSISTENCE_FAILURE` 類別，並傳回 `CHAIN_SEED_POST_SUBMIT_PERSISTENCE_RECOVERED`。重新開啟相同的環境並重新執行 bootstrap：它等待已儲存的雜湊並且不會再次呼叫提交。任何哈希之前的失敗仍然是 `SUBMIT_OUTCOME_UNKNOWN` 並需要操作員審查。

日誌回歸測試注入瞬態雜湊後寫入錯誤，並證明重新開啟的日誌無需第二次提交即可驗證原始雜湊。無哈希提交失敗、擱淺的 `PREPARED` 步驟、更改的意圖和更改的接收證據仍然會失敗關閉。

## 託管綁定步驟

新的 bootstrap 部署 `VehicleNFT`，部署 `MotorCoveEscrow`，然後在鑄造演示代幣之前記錄 `bind-vehicle-nft-escrow` 交易。綁定是一次性的，交易收據是鏈種子日誌的一部分。透過讀取 `VehicleNFT.motorCoveEscrow()` 並將結果與清單託管位址進行比較來驗證它。只有當鏈上綁定仍然匹配時，現有清單才會被接受；缺少 getter 或不同的位址會在資料庫引導之前返回 `DEPLOYMENT_MISMATCH`。

使用此綁定之前的合約字節碼所建立的環境無法就地升級；合約是不可升級的。保留該環境以供檢查或在引導全新部署之前執行明確本機重設工作流程。 Bootstrap 絕不會隱含重置或取代現有環境。

## Bootstrap 完成 sidecar

Bootstrap 將 `deployment.json` 和 `bootstrap-receipt.json` 發佈為完全不可變的 JSON sidecar：驗證、寫入和刷新操作唯一的臨時文件，重命名到位，並同步包含的目錄。復原時，現有的最終檔案必須解析並匹配其環境和部署。收據還驗證其目標區塊/哈希、投影建置 ID 和完成時間。它的目標和構建ID是歷史完成的證據；稍後的交易可能會推進鏈頭，並且有效的重建可能會使用不同的當前投影構建。部署的標準備份需要此收據和配對種子日誌。格式錯誤或衝突的最終內容會停止明確復原操作。
