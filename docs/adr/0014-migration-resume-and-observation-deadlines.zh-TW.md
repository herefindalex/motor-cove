# ADR 0014：遷移延續與有界事務觀察

[English](0014-migration-resume-and-observation-deadlines.md) · [简体中文](0014-migration-resume-and-observation-deadlines.zh-CN.md)

- **狀態：**已接受
- **日期：** 2026-09-22

## 背景

中斷的遷移留下了兩個有效狀態之一：未更改的已知遷移前綴，或 `db_contract` 最終確定先前的當前 SQL 架構。持久性 `MIGRATE` 標記無法識別目標遷移包，因此遷移命令拒絕每次重試，而通用復原可以在不完成元資料的情況下清除目前架構標記。

瀏覽器事務恢復也有兩個不對稱的生存期規則。 HTTP 回應正文可以在標頭到達後保持掛起狀態，並無限期保留觀察者單次飛行時隙。成功的收據仍處於自動本地觀察狀態，而恢復的收據則停止。

## 決定

1. 新的遷移標記記錄了預期的模式契約和遷移包摘要。一個
   只有當操作、環境、資料庫路徑、模式契約和套件摘要全部匹配時，遷移才可以繼續現有標記。
2. 恢復在採取行動之前會驗證本地歷史。已知的舊前綴保持標記並返回
   `RERUN_MATCHING_MIGRATION`。目前模式經過驗證，其 `db_contract` 元資料從檢查的儲存庫合約中最終確定，再次驗證為來源資料庫，然後才清除其標記。未知的歷史記錄、模式漂移和身份不匹配仍然無法解決。
3. Web HTTP 適配器為標頭和正文消耗提供了一個 AbortController 截止時間。超時
   中止底層的fetch，透過恢復路徑記錄現有的不可用驗證結果，並釋放Observer單次插槽。
4. `INCLUDED_SUCCESS`和`INCLUDED_REVERTED`使用相同的局部非最終自動觀測
   政策。錢包被拒絕和提交前失敗的情況仍然被排除在外。該策略支援重組和相同哈希重新包含檢測；這不是公共網路的最終聲明。

## 後果

- 操作員可以恢復確切的遷移包，而無需刪除持久的故障證據。
- 當來源合約元資料過時時，SQL 提交後的崩潰無法報告復原。
- 停滯的反應主體具有有限的生命週期，並且不會永久抑制以後的唯讀
  驗證嘗試。
- 恢復的收據可以前進到孤立或重新包含的證據，而無需手動按下按鈕。
